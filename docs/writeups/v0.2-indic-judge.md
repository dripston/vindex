# Your LLM judge doesn't understand what it just read

The first post about `vindex` was a script bug: ask a model to "reply
in the same language and script," phrase the question in Romanized
Hindi, and four times out of five you get Devanagari back. Cheap to
find, cheap to fix, `script_adherence` catches it in one line.

This post is about a harder bug, in the piece of the stack that's
supposed to catch bugs: the LLM judge.

## The setup

`vindex` needed a way to score whether a Hindi answer was factually
correct with no reference answer to compare against -- reference-free
judging, which means an LLM has to do the actual reasoning. Off-the-shelf
judge prompts are written in English: "You are an expert evaluator.
Score this answer from 0 to 1." Point one at Hindi input and it works,
mostly. "Mostly" turned out to be doing a lot of work.

## The bug

समुद्र तल पर पानी किस तापमान पर उबलता है? -- "at sea level, what
temperature does water boil?" समुद्र तल means "sea level." An
English-reasoning judge, mid-chain-of-thought, translated it as "sea
floor" -- a real word, a plausible mistranslation, and a completely
different question. The answer correctly addressed sea level. The judge,
having silently swapped in "sea floor" three sentences into its own
reasoning, scored it 0.0.

The interesting part isn't that an LLM mistranslated a word. It's
*where*: not in the final verdict, where you might sanity-check it, but
inside the reasoning trace the judge itself generated on the way to a
verdict. Nothing downstream sees that trace as suspicious. The score
comes out looking exactly like a normal, confident 0.0.

## Two fixes, not one

**Fix one: `indic_judge`.** Write the rubric in Hindi, not English
translated into a prompt template. Default to reference-free (this
project's own data showed a gold reference measurably *masks*
comprehension drift -- the judge anchors on the reference instead of
actually reading the question). Make it conservative by design: an
ambiguous case comes back `label="flagged"`, not a silent pass.

**Fix two, the one that actually matters here: `check_trace`.** You
cannot fix "the judge silently mistranslated a word in its own
reasoning" by writing a better judge prompt -- that's the same failure
mode with extra steps. What catches it is something outside the judge
entirely: a dictionary of known ambiguous Hindi terms (समुद्र तल /
"sea floor" vs "sea level" is one of 70), checked mechanically against
whatever reasoning trace a judge produced. No LLM call, no meta-judge,
free, instant, reproducible. It works on *any* judge's trace, not just
`indic_judge`'s own -- pass it text from GPT-4, from your own
in-house judge, whatever produced the reasoning.

The honest scope, stated the way Milestone 6.2 requires: this catches
mistranslation of *known* ambiguous terms, not mistranslation in
general. A term not yet in the dictionary needs the LLM-fallback mode
instead (align-then-judge, Sarvam's shape -- diff first, model only on
what doesn't align).

## Validating it honestly

Building a judge and a judge-checker is the easy 80%. The other 20% is
not skipping the part where you find out if it actually agrees with a
human -- and this project has an obvious conflict of interest doing
that: the person grading is also the person who built the metric.

So the grading ran under a written bias protocol
(`docs/annotation/BIAS_PROTOCOL.md`), fixed before a single trace was
graded: ground truth committed to git first (so it can't be quietly
adjusted after seeing results), a blinded sheet with no model identity
or judge verdict visible, a frozen rubric, a 30% holdout neither grader
touched until both full sets were submitted, and a second grader with
no stake in the result.

62 traces, 31 trap words each seeded correct and wrong.

```
--- TUNING SET (43 traces) ---
  grader1 vs grader2 (inter-annotator): 43/43 = 100.0%
  grader1 vs indic_judge:                38/43 = 88.4%
  grader2 vs indic_judge:                38/43 = 88.4%

--- HOLDOUT SET (19 traces) ---
  grader1 vs grader2 (inter-annotator): 19/19 = 100.0%
  grader1 vs indic_judge:                18/19 = 94.7%
  grader2 vs indic_judge:                18/19 = 94.7%

--- ALL (62 traces) ---
  grader1 vs grader2 (inter-annotator): 62/62 = 100.0%
  grader1 vs indic_judge:                56/62 = 90.3%
  grader2 vs indic_judge:                56/62 = 90.3%
```

90.3% agreement between two independent human graders and
`indic_judge`'s own verdict. No meaningful gap between the tuning set
and the untouched holdout, so no evidence the graders drifted toward
the judge's patterns as grading went on. Every disagreement was the
same shape: a correct answer the judge marked `flagged` over an
edge-case nuance -- the conservative-by-design failure mode, not a
missed mistranslation.

**Disclosure, stated next to the number every time it's cited:** one of
the two graders is the project owner, who also built the metric being
evaluated. The second grader is an independent fluent Hindi speaker
with no stake in the result. 100% inter-annotator agreement between two
humans is itself a real, checkable number -- it isn't a substitute for
that disclosure, and the 90.3% figure should never be quoted without it.

**What this number is not:** a comparison against an English-rubric
judge on the same traces. The motivating claim for writing a Hindi
rubric in the first place -- that it beats an English one pointed at
Hindi -- was unmeasured on this dataset at the time this was first
written.

**Update: that comparison has since been run (Milestone 5.8), and the
result is not the one this post's argument would predict.** An
English-rubric baseline, structurally identical to the Hindi rubric
above except for the rubric's language, agreed with the same human
graders slightly *more* than `indic_judge`'s Hindi rubric on these 62
traces: 93.5% (58/62) vs 90.3% (56/62). Inspecting the 4 disagreements
shows this isn't the English judge avoiding a mistranslation the Hindi
one made, or the reverse -- it's `indic_judge` being more conservative
about answer completeness (flagging a factually correct answer for
omitting a secondary detail the question didn't ask for), slightly
more often than the English rubric does on this sample. Reported
honestly rather than quietly left as "still open": the mechanism
argument earlier in this post (no translation step, so no mistranslation
can hide inside it) still explains the one documented Phase 0 failure
it was built to fix, but it does not, on this evidence, mean the Hindi
rubric out-agrees a human grader more than an English one would in
general. Full breakdown, per-trace reasoning, and the honest read on
what this does and doesn't show: `experiments/README.md`'s Milestone
5.8 section.

## What shipped in v0.2

- `indic_judge` -- Hindi-rubric, reference-free-by-default LLM judge
- `check_trace` -- dictionary-based mechanical check for known
  mistranslations inside any judge's reasoning trace, plus an
  LLM-fallback mode for categories a fixed dictionary can't catch
- The validation above, numbers included, whatever they turned out to
  be

Install: `pip install vindex[judge]`. Full example and the complete
limitations list (there are more than the ones in this post) in the
[README](../../README.md).
